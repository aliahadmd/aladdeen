# Markdown preview improvements

Research date: 2026-11-13. The proposal below records the original recommendations; implementation and verification are recorded at the end.

## Recommended first change

Add a small square **Expand diagram** button at the top right of every successfully rendered Mermaid block. It should open a full-window, accessible diagram viewer with scroll-to-zoom, drag-to-pan, visible zoom controls, **Fit**, **100%**, and **Close**. Keep normal document scrolling unchanged until the viewer is opened.

The screenshot's wide flowchart is compressed into the available preview width. Local code confirms the mechanism: [`MermaidDiagram.tsx`](../../src/renderer/src/components/MermaidDiagram.tsx) renders a sanitized SVG without controls, and [`.mermaid-svg svg`](../../src/renderer/src/index.css) applies `max-width: 100%; height: auto`. Enlarging the containing window alone can still leave a very wide graph unreadable; the viewer needs an independent scale and pan position.

## Evidence and design decisions

**Use an in-app modal for the first Expand action.** A modal must contain keyboard focus, make the background inert, close with Escape, and return focus to the invoking control. A visible close button and an accessible title are part of the intended interaction. [WAI-ARIA modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

**Recommendation:** use the project's existing Radix Dialog dependency, sized to the application viewport, so expansion does not depend on entering macOS display fullscreen. Radix already supplies modal focus handling and Escape dismissal. True display fullscreen can remain a secondary action; `requestFullscreen()` is asynchronous, requires user activation, and needs failure handling. If enabled, Escape should leave native fullscreen first; a subsequent Escape can close the expanded viewer. [Radix Dialog](https://www.radix-ui.com/primitives/docs/components/dialog), [Fullscreen API](https://developer.mozilla.org/en-US/docs/Web/API/Element/requestFullscreen)

**Honor plain scroll-to-zoom only in the expanded canvas.** Wheel events can come from a mouse or trackpad; a pinch gesture can also produce wheel events with `ctrlKey`. The interface exposes deltas and modifier state, so automatic mouse-versus-trackpad classification should not be treated as reliable. **Recommendation:** show “Scroll to zoom · Drag to pan” in the viewer; plain vertical wheel input zooms, horizontal input pans, and drag, keyboard arrows, scrollbars, or directional controls move the view. If ordinary two-finger vertical scrolling should pan, provide an explicit Pan/Zoom scroll-mode switch. Do not promise automatic plain-wheel zoom and two-finger scroll panning at the same time. [Wheel event](https://developer.mozilla.org/en-US/docs/Web/API/Element/wheel_event)

**Normalize zoom input and anchor it.** Scale should change continuously according to delta magnitude and `deltaMode`, with the content under the cursor held still. The documented D3 zoom implementation normalizes pixel/line/page wheel deltas and uses exponential scaling; its programmatic scale methods support an anchor point. **Recommendation:** adapt the existing mindmap anchoring logic and use proportional input, instead of a fixed 25% jump for every trackpad event. Use a scoped non-passive listener only on the expanded canvas, prevent its handled default action, and remove it on close. [D3 zoom API](https://d3js.org/d3-zoom), [Wheel event cancellation](https://developer.mozilla.org/en-US/docs/Web/API/Element/wheel_event)

**Provide visible single-pointer and keyboard alternatives.** Pinch must have simple pointer alternatives, and custom drag panning needs an equivalent operation that does not require dragging. Keyboard access alone does not satisfy that second requirement. **Recommendation:** clickable zoom buttons, Fit and 100%, native scrollbars or four pan buttons, and focused-canvas `+`, `-`, `0`/Fit and arrow-key commands. Keep the modal Tab sequence conventional. [Pointer gestures](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html), [Dragging movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)

**Keep the square control easy to find and activate.** Recommendation: 32 × 32 CSS px with a 16 px expand icon, visible keyboard focus, tooltip, and accessible name “Expand diagram”; keep it present rather than hover-only. The WCAG minimum target-size criterion generally requires 24 × 24 CSS px or sufficient spacing, subject to exceptions. The proposed 32 px size is a product choice above that minimum. [Target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

**Check contrast as well as scale.** Recommendation: qualify default diagram labels against a 4.5:1 text-contrast target and meaningful controls/graphical connections against the applicable 3:1 non-text criterion, accounting for the standards' exceptions. Check actual rendered foreground/background colors in light and dark themes. The screenshot motivates this check but is not evidence of a measured contrast failure. [Text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [Non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

**Preserve the vector and accessible description.** Mermaid supports `accTitle` and `accDescr`, producing SVG title/description and ARIA relationships. The shipped Mermaid distribution also contains the ARIA title/description code; no Mermaid upgrade is required for this direction. Recommendation: use these values for the dialog title or a concise description when available, otherwise provide a neutral fallback and a **Source** view. Do not label every diagram only “Mermaid diagram” when authored context exists. [Mermaid accessibility](https://mermaid.js.org/config/accessibility.html), [local renderer](../../src/renderer/src/components/MermaidDiagram.tsx)

**Avoid duplicate SVG identifiers when expanding cached markup.** IDs must be unique within their node tree. The current cache reuses a rendered SVG string, so copying that markup into a second inline instance can duplicate marker, clip-path, style-selector, and ARIA references. Recommendation: either namespace every ID and all references per rendered instance, or isolate the already-sanitized SVG in a Blob-backed image for the expanded view. The image option retains vector rendering and isolates the SVG document, but loses inner text selection and per-node semantics, so it needs an explicit alternative label/source view. Keep the existing sanitizer and network restrictions. Revoke Blob URLs when no longer used. [SVG IDs](https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Attribute/id), [SVG image contexts](https://developer.mozilla.org/en-US/docs/Web/SVG/Guides/SVG_as_an_image)

## Proposed interaction contract

- Inline: retain the fit-to-width overview and original document scroll position; reserve control space so the expand button covers no graph labels.
- Open: begin at readable **100%** for wide graphs, with pan/scroll available and a separate **Fit** overview action. The screenshot already uses nearly the full available width, so enlarging at Fit can still leave labels tiny. Define 100% as one SVG `viewBox` unit per CSS px; derive dimensions from the sanitized SVG's viewBox and preserve its aspect ratio. For small diagrams, keep natural size rather than stretching them to fill the window.
- Fit: use `min(viewportWidth / graphWidth, viewportHeight / graphHeight, 1)` after toolbar and padding are subtracted. This is an overview, not a promise of readable labels. Preserve the reader's chosen zoom/pan when reopening unchanged content during the session if practical.
- Zoom: proposed range 5–800%, extended downward when Fit needs less than 5%; clamp user input without jumping above an already-smaller fit scale. Keep Fit separate from the user's deliberate zoom and preserve that zoom on resize. Refit on resize only while Fit mode is active.
- Pan: prevent losing the graph entirely offscreen; preserve cursor position while zooming. Do not animate each wheel event. A short opening fade is optional and should respect reduced motion.
- Close: restore the exact document scroll position and focus to its expand button. Changing documents or unmounting the preview closes the viewer and releases listeners/Blob URLs.
- Invalid or loading diagrams: retain the existing loading/source-error fallback; disable expansion until usable SVG is available.

These numeric limits and control choices are recommendations, not standards requirements.

## Implementation boundaries and verification

Create a reusable expanded-content shell with a small zoom/pan controller. Keep Mermaid rendering and sanitization in `MermaidDiagram.tsx`; opening or zooming should reuse the finished SVG, with no new Mermaid render for each event. Reuse the current mindmap anchor math where practical, but avoid tying the general viewer to the mindmap's dark code-block styling.

Share the shell, close behavior, and focus handling across block types; enable graphical zoom for diagrams/images. Keep tables and code as selectable semantic content with native scrolling and optional wrapping. Expanding a table or code block should give it more room without shrinking its text.

Pass the existing `interactive` flag through `MarkdownContent` → `MarkdownCodeBlock` → Mermaid/mindmap controls. The export renderer uses the same pipeline with `interactive={false}`; interactive chrome and modal state must stay out of PDF export. Preserve original source offsets and use the existing `data-preview-source-ignore` boundary for viewer controls, so clicking Expand, zooming, or panning never jumps the editor to source. [Markdown renderer](../../src/renderer/src/components/MarkdownContent.tsx), [export renderer](../../src/renderer/src/export-main.tsx), [export styles](../../src/renderer/src/export.css)

The existing application-wide keyboard handler must also respect modal focus and `defaultPrevented`: scope viewer shortcuts to its canvas and prevent document commands from firing underneath the modal. Hiding only `.code-block-toolbar button`, as export CSS currently does, will not automatically hide new controls outside that toolbar. [Application keyboard handling](../../src/renderer/src/App.tsx)

Verify the screenshot's wide graph, a tall sequence diagram, a small graph, repeated identical graphs, authored accessibility titles, dark/light themes, source errors, live edits, and a narrow window. Interaction checks should cover keyboard-only open/close and focus return, pointer-anchored zoom, line/pixel wheel deltas, trackpad pinch, plain wheel behavior in each mode, pan alternatives, preservation of reading position, offline/network guards, and exports without controls. Existing Mermaid and mindmap tests provide the starting fixtures; test real Mac mouse and trackpad behavior in Electron as well as deterministic zoom math in unit tests.

## Implementation and verification — 2026-11-13

Implemented the shared expanded viewer for Mermaid, mindmaps, local images, overflowing tables and equations, and code blocks. Diagrams start at native scale with pointer-anchored scroll zoom, drag panning, pan buttons, keyboard controls, Fit, 100%, and source view. Images initially fit the viewer. Tables retain semantic cells and sticky headers; code retains syntax highlighting, raw Copy, and optional wrapping. Equations retain MathML and offer their LaTeX source. The outline now includes H1–H3 and can filter to top-level headings. Callout typography received a small refinement.

Cached inline SVG instances have independent identifiers; expanded SVGs use isolated image documents. Mindmap downloads now contain computed presentation styles. Preview controls are omitted when `interactive={false}` and app shortcuts respect the expanded modal. The shared dialog restores reading position and focus on close.

Validation: production build/typechecking, ESLint, 212 unit tests across 40 files, and 20 Electron end-to-end tests passed. The end-to-end coverage includes pointer anchoring, drag/button panning, keyboard zoom and focus containment, source views, repeated diagrams, sticky headers, SVG download styling, compact dark mode, and existing PDF/DOCX exports. Physical trackpad feel has not been manually evaluated; wheel normalization has deterministic unit coverage and Electron pointer/wheel coverage.

The original settings screenshot mismatch was also reproduced on unchanged `9a1cf11`. The test now selects themes through the actual settings controls instead of changing root CSS classes independently of application state. Its dark-mode baselines were reviewed and updated, and the full Electron suite passes without exclusions.
